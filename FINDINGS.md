# Findings & Implementation Detail

This is the detailed companion to [DESIGN.md](DESIGN.md), which is intentionally kept to the
1-2 pages the assignment asks for. Everything here was moved out of DESIGN.md, not deleted -
the bug-by-bug history in particular is real evidence of how this project was actually built
(live-tested and audited, not assumed correct), and felt more valuable to preserve in full than
to summarize away.

## 1. State management detail

`ConversationState` has five values: `AWAIT_ACCOUNT_ID, AWAIT_IDENTITY, AWAIT_AMOUNT, AWAIT_CARD_DETAILS, CLOSED`. Account lookup and payment processing are *not* separate states, even though the assignment's suggested list includes them — both API calls are synchronous and complete within the single `next()` call that triggers them, so there's never a turn boundary where the agent is "in" a lookup. Which actions actually happened is recorded separately in `session.action_log` (e.g. `"lookup_account:success"`, `"verify_identity:failed"`) — that's what the eval suite checks tool-call sequences against, independent of the state enum.

Extracted fields are merged into `Session` every turn, regardless of current state (this is what makes early-volunteered and out-of-order information work), with two guards: identity fields stop being overwritten once `verified=True` (they're locked in), and nothing is merged once the session is `CLOSED`. Card/amount fields captured before verification just sit unused in `Session` — they're never read until the handler chain actually reaches `AWAIT_CARD_DETAILS`/`AWAIT_AMOUNT`, which structurally cannot happen before `AWAIT_IDENTITY` succeeds.

A single-word name claim (e.g. "urvi") is deliberately *not* immediately used as a verification attempt. It's certain to fail against a real two-word account name, and attempting it anyway would burn a retry on what's really an incomplete answer, not a wrong guess. `agent._handle_identity()` nudges once via a one-shot `session.name_clarification_asked` flag, then accepts whatever's given next (even another single word) as the real answer — this is what stops the nudge from becoming a *new* infinite loop for an account whose real name genuinely is one word.

## 2. Live-testing findings log

**What live testing (and, most recently, an external audit) turned up, in order found** — every LLM call and every deterministic path in this project has, at some point, produced a real bug that a mocked test suite alone would not have caught:

*Understanding side (live Groq testing):*
1. `full_name` extraction on a nickname-then-formal-name pattern ("it is Nithin, Nithin Jain") initially returned the literal `"Nithin, Nithin Jain"` instead of just `"Nithin Jain"`. Not a security problem — `verify_identity()` correctly rejected it as a non-match. Fixed with an explicit instruction and example in the system prompt.
2. `expiry_year` extraction on a 2-digit year ("expiry 12/27") returned `expiry_month=12` but left `expiry_year` null — the schema description said "4 digits," read as "don't fill this in unless already 4 digits." Fixed by rewording the field description to instruct expansion explicitly.

*Phrasing side:*
3. A rephrased response was silently truncated mid-sentence. Cause: the default Groq model is a reasoning model that spends completion tokens on invisible chain-of-thought before writing the visible reply; a 150-token budget left too little room, and the call returned `finish_reason: "length"` mid-answer. Fixed by passing `reasoning_effort="low"`.
4. For a template with no numeric facts to check, the model sometimes tried to *answer* the message instead of rewording it (one run: "I'm sorry, but I can't share that"; another: role-playing as the customer). The fact-preservation check didn't catch either, since it only checks facts present in the template — one with none passes vacuously. Fixed by wrapping the template in explicit delimiters (`<<<...>>>`) and framing the task as "rewrite this," not a bare chat turn.

*Found by a live tester actually using the finished web UI, not by scripted testing:*
5. **The most serious finding prior to this round.** `full_name` extraction on a lowercase input ("nithin jain") returned `"Nithin Jain"` — correctly title-cased, and completely wrong to return, since `verify_identity()`'s strict `==` would then silently match the account's stored name. This would have meant the *model*, not the deterministic check, effectively decided the name matched. No prompt wording was trusted to fix this a second time: `agent._cross_check_with_regex()` now requires the extracted name to appear character-for-character in the user's actual message, or it's discarded in favor of regex's verbatim-copy behavior. A deterministic, structural guarantee, not a prompt that might work.
6. A related bug the more lenient LLM extraction exposed: `agent._handle_card_details()` only validated card fields once *all three* were present, so an invalid card number given before the others sat unvalidated. Fixed by validating each field the moment it's set.
7. A latency bug: individual failed LLM calls were taking 17-39 seconds before falling back. Cause: the `openai` SDK retries a failed call itself (`max_retries=2` default) before ever raising the exception this code catches. Fixed by passing `max_retries=0` — this project already has its own fallback, so there's no value in the SDK spending seconds retrying first. Confirmed live: 17-39s calls dropped to 0.4-2s.
8. The rate limit in finding 7 wasn't transient — sustained quota exhaustion from live testing volume. Motivated adding a second provider (OpenRouter) as a fallback. Getting it working took two more rounds of live-testing-over-assumption: the first free model rejected a *forced* tool choice outright; a second accepted forced tool choice but was unreliable with `tool_choice="auto"` (same input, two different outcomes across two runs); a third model was tested and confirmed reliable across three consecutive runs before shipping. Lesson: "provider X is OpenAI-compatible" only guarantees request/response *shape*, not that every capability behaves the same way underneath.
9. The extraction fallback pairing had one more gap: the LLM path can return a genuinely *partial* extraction from a compound message and still count as a successful tool call (one live run picked up only the expiry from a message with a card number, expiry, and CVV all present, silently dropping the other two). Fixed by having `agent._cross_check_with_regex()` always run the regex parser after *any* successful LLM extraction and fill in whatever field the LLM left null — the same "gap-filling, not full override" principle as finding 5, generalized to every field.
10. A round of conversational-quality feedback (not a correctness bug) found the extractor had no visibility into what the session already held, no way to end a conversation on request, and phrasing had no lever for tone. Added `ExtractedFields.intent` (`cancel`/`small_talk`/`balance_query`/`None` — the *only* new thing an extractor can return that `agent.py` acts on directly, via one unconditional check), `agent._llm_session_context()` (a small filtered dict so a short reply can be read against what's already known), and a `tone_hint` string (phrasing-only, still subject to the same fact-preservation check).
11. A closer look at `responder.py` found it had only the bare template and current state name to work with, so even a warm rewording could only ever be mechanical. Added `agent._response_checklist()` — a short, plain-English "what we know so far" list, same non-sensitive scope as the extraction context. Building this surfaced two real bugs: (a) the account-ID correction `tone_hint` could fire even after an account had already been successfully looked up, telling the phrasing step to describe a switch that never happened (fixed by gating the check on still being in `AWAIT_ACCOUNT_ID`); (b) `_merge_extracted()` applies a newly-extracted amount unconditionally regardless of state, so a corrected amount given *after* the first was already accepted could skip `validate_amount()` entirely (fixed by re-checking the amount against the balance at the top of `_handle_card_details`). A third, smaller bug in this round: the CVV bare-number fallback required the *entire* message to be nothing but the digits, so a natural "It's 123" follow-up was silently dropped — loosened to trust a lone digit sequence even when it wasn't the whole message. **This fix is what caused finding 13 below**, and was reverted this round.
12. A cleanup pass (not new behavior) found `responder.SYSTEM_PROMPT` instructed the model to preserve "attempt/retry counts," but `_facts_preserved()`'s regex only ever checked `₹`/`ACC`/`txn_` patterns — a free-form number like "2 attempts left" could be rephrased away and nothing would catch it. Rather than widen the regex (fragile, easy to get subtly wrong), `agent.next()` now computes a `security_critical` flag (a verification failure stating a retry count, or any conversation-closing message) and skips the LLM step for those entirely — the message shown is always the exact deterministic text.

*Found by an external final-submission audit, not this project's own testing:*
13. **The most serious finding in this project, superseding finding 5.** Finding 11's CVV fallback loosening ("trust a lone digit sequence even when it's not the whole message") was too broad: any message received in `AWAIT_CARD_DETAILS` containing exactly one 3-4 digit number got read as the CVV, with zero relation to what the message was actually about. Confirmed live: with card number and expiry already given and CVV the only missing field, sending `"actually pay 700"` (a message entirely about correcting the payment amount) set `session.cvv = "700"` — and since all three card fields were now "present," triggered `process_payment` immediately, submitting a real payment with a CVV the user never stated as a CVV. The agent never asked for the actual CVV at all. `"my card expires in May 2028"` and even unrelated small talk like `"call me back at 234"` had the same failure mode. This is qualitatively worse than finding 5: not a decision made from slightly-wrong data, but a payment submitted using a value fabricated from unrelated text. Root cause: "this is the one digit group in the message" is a necessary but nowhere near sufficient condition for "this message is stating a CVV." Fixed by removing every unlabeled/bare CVV fallback entirely, including the original, longer-standing exact-bare-match rule (a standalone `"111"` with literally nothing else in the message) — `extractor._extract_cvv` now requires an explicit label (`"cvv 123"`, `"security code 123"`, `"security number 123"`, or a spelled-out CVV) before ever returning a value. The underlying principle: **ambiguous numeric input must never be interpreted as sensitive card data.** A genuinely unlabeled short reply (`"it's 123"`) is no longer handled by the regex fallback at all — that's correctly the LLM path's job, since it has `agent._llm_session_context()` (which field is actually still missing) to resolve the ambiguity from context, not digit shape alone. The same audit found two lower-severity extraction gaps, both fixed the same round: a bare account ID with no `"ACC"` prefix embedded in a sentence (`"my account is 1001"`) previously required the *entire* message to be nothing but digits; now anchored on the word "account" (the same keyword-proximity pattern already used for Aadhaar/pincode, deliberately *not* "the one digit group in the whole message," since that broader pattern is exactly what caused this finding) — and `"I'll pay the whole thing"` not matching the full-balance phrase list. It also found one narrow prompt-injection surface: an extracted `account_id` was interpolated into the responder's `tone_hint` before `validate_account_id()` had run on it — closed by validating first. None of these three secondary fixes touch business-logic decisions; the CVV fix is the only one with a confirmed payment-integrity consequence.

**What this log demonstrates, read end to end**: findings 1-4 came from methodical live testing; 5-7 and 11's regression came from a person actually using the feature or building on top of it; 13 came from an external audit applying adversarial pressure this project's own testing hadn't yet applied. No single testing method here was sufficient on its own — each caught a different failure shape, and 13 in particular is a reminder that "the regex fallback is deterministic" was never the same claim as "the regex fallback is correct."

## 3. Verification design detail

`verification.py` is one pure function: exact string equality on full name, AND exact equality on at least one of DOB/Aadhaar-last4/pincode among whatever the user actually supplied (fields not supplied are simply not compared, not treated as a mismatch). No `.lower()`, no whitespace normalization, no partial matches. This function never sees an LLM output — it's called from `agent._handle_identity()` with values already merged into `Session` by the extractor.

Retry handling lives in `agent.py`: three wrong attempts closes the conversation. Every rejection message is deliberately generic ("those details don't match our records") — it never states which field was wrong, so repeated attempts can't be used to narrow down a guess. A structurally invalid secondary factor (Feb 30, or Feb 29 in a non-leap year — the ACC1004 case) is caught by `validators.validate_dob()` *before* being handed to `verify_identity()`, and does not count as a failed attempt, since it's a typo/format problem, not a wrong guess.

## 4. Tool/API design detail

`tools.py` wraps both endpoints with a 10s timeout and one automatic retry on connection/timeout errors, then raises `ApiUnavailableError` — every retryable failure funnels through one exception type. Business outcomes (found/not-found, success/error_code) are returned as typed dataclasses, not raised as exceptions.

Probing the real API during development found a gap between its documentation and behavior: `process-payment` returns the documented per-field codes at HTTP 422, but returns a generic `400 {"error_code": "invalid_args"}` for *any* expiry problem and for malformed amounts — never the documented `invalid_expiry`/`invalid_amount` codes for these specific cases. Since `validators.py` already validates both locally before ever calling the API, this gap turned out not to matter in practice — but it's exactly why local validation is a requirement, not a nicety.

## 5. Failure handling detail

Three categories: **user-fixable** (invalid card/CVV/expiry/amount) — local validators catch most before any API call, whatever the API itself rejects maps through `agent.PAYMENT_ERROR_ACTIONS` to a specific message and routes back for another attempt. **Retryable** (network/timeout/malformed response) — surfaces as `ApiUnavailableError`, session state left unchanged so the same input can be retried. **Terminal** (any retry limit exceeded) — moves to `CLOSED` with a fixed message every subsequent call repeats verbatim.

One narrow top-level `try/except Exception` sits in `Agent.next()` as a backstop against a genuine bug — every expected failure mode is handled explicitly and never reaches it. It logs the exception and returns a generic apology without touching session state.

## 6. Security decisions detail

- Card number/CVV are never logged — `tools.py` logs only whitelisted fields, never request/response bodies or raw user input.
- Raw card fields are cleared from `Session` immediately after every payment attempt, success or failure.
- DOB/Aadhaar/pincode are read from the account API only to feed `verify_identity()`'s in-memory comparison; no code path ever places them into a user-facing message.
- The one real secret, the LLM API key, is read from the environment only, is optional, and is never logged or echoed into any prompt.
- `llm_extractor.py` and `responder.py` each receive only a small, explicitly-filtered context dict/checklist built by `agent.py` — never `Session` or `Account` directly.
- The extracted `full_name` must appear verbatim in the user's raw message or it's discarded in favor of the regex parser's output (finding 5) — the sharpest concrete example in this project of "LLM proposes, deterministic code disposes" enforced by code, not prompt wording.
- Ambiguous numeric input is never interpreted as sensitive card data — CVV extraction requires an explicit label (finding 13).

## 7. Evaluation methodology detail

Two layers: **`tests/`** (126 pytest tests) — unit tests for pure functions plus integration tests for `agent.py` with both APIs mocked. `llm_extractor.py`/`responder.py` each tested with a faked OpenAI-compatible client. An autouse fixture force-disables both real LLM paths for the rest of the suite, so it's fast, offline, and behaves identically regardless of whether an API key is set. **`evals/`** — 38 scripted multi-turn conversations against the real live payment API, asserting final action-log sequence, state classification, and specific session field values, not just the final message. `evals/evaluation.py` aggregates these into the metrics the assignment asks for and writes `evals/results.json` for debugging a failure.

Historical note on how the LLM-configured path was validated: the regex/template-only path was developed and verified first (no key required), then the live LLM path for understanding only, then the full live LLM path for both understanding and phrasing, once a Groq key became available. None of the LLM-path runs passed on the first try — see the findings log above for exactly what each pass turned up (two extraction bugs, two phrasing bugs, and confirmation that both fallback mechanisms fire for real under an actual rate limit and an actual malformed request, not just in a mock). **This history predates finding 13 and the current 38-scenario set** — before submitting, re-run `evals/evaluation.py` with a real key configured and treat that as the current source of truth for the LLM-path claim, not this note.

## 8. Tradeoffs — fuller reasoning

- **LLM-first extraction and phrasing, both with deterministic fallbacks**, rather than any all-or-nothing combination. A pure-LLM design would be simpler to maintain but would fail the "deterministic across repeated runs" requirement whenever the key/network isn't available — not hypothetical, since a rate limit and a malformed request both actually occurred during live eval testing. A purely deterministic design (this project's first iteration) works standalone but caps NL understanding at anticipated patterns.
- **Response phrasing as rewording, not generation from an abstract state description.** The alternative — handing the model `{"state": "AWAIT_IDENTITY", ...}` and letting it compose the sentence — would require the model to get the *content* right every time, with a much harder validation problem on the output. Finding 4 (the model trying to answer instead of reword) suggests even the smaller task needed real effort to get reliable.
- **Groq via an OpenAI-compatible client**, not a provider-specific SDK — one code path covers Groq, OpenAI, and OpenRouter, at the cost of depending on that compatibility holding rather than a first-party SDK's closer fit.
- **A cascading `if`-chain**, not a state-machine framework — cancellation fit in as a single early check rather than a new state, since it's a short-circuit, not a branch. A genuinely branchy addition (multiple payment methods) would need revisiting this.
- **Cardholder name silently defaults to the verified account name** unless stated otherwise — reduces friction since the API doesn't check this field against the account anyway, at the cost of one implicit assumption.

## 9. Future improvements — fuller list

- Property-based/fuzz testing of `extractor.py` (e.g. Hypothesis) to search for more field-disambiguation bugs of finding 13's shape, rather than relying on enumerated examples — this matters more, not less, now that it's the fallback of record whenever the LLM path is unavailable.
- Broaden adversarial live-LLM testing specifically — most real bugs found so far came from live use or external audit, not the scripted suite; add latency to what the eval suite measures too (finding 7 would have been visible as "this scenario took 35s" well before anyone noticed by hand).
- Generalize finding 5's verbatim-match defense beyond `full_name` to any extracted field where a model might "improve" what the user actually said instead of copying it.
- A stronger fact-preservation check for the ordinary (non-security-critical) messages finding 12's fix doesn't cover — a wrong-but-fact-free rewording (finding 4's case) still only has the `₹`/`ACC`/`txn_` check to catch it.
- A "start a new payment" flow after `CLOSED`, instead of requiring a fresh `Agent()`.
- Structured (JSON) logging with a correlation ID per conversation, for a real deployment.
